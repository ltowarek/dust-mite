# AFK loop triggers: comment commands, labels and the `pull_request_target` block

Date: 2026-11-15

## Summary

GitHub blocks `pull_request_target` by default in public repositories from 2026-12-02. The block does not apply where an Actions event policy allows the event, and this repository already holds a repository-level Actions policy, so an exception scoped to [afk-run-pr.yml](../../.github/workflows/afk-run-pr.yml) and [afk-update-branch.yml](../../.github/workflows/afk-update-branch.yml) is available. All first-party coding agents that run in Actions use comment mentions (`@claude`, `@gemini-cli`, `/command`) as their primary trigger. They check the commenter's repository permission through the collaborator-permission API, report progress with a reaction or a tracking comment, and also accept labels or assignment. The Copilot cloud agent is triggered by assignment and `@copilot` mentions, and only by users with write access. It is not an Actions workflow, so its trigger model does not transfer directly.

`issue_comment` is not affected by the block and runs on conflicting PRs, but it has drawbacks. GitHub enforces nothing about who may comment, so the workflow must authorise the commenter itself. Every comment, including the App's own, starts a run. GitHub Security Lab documents a TOCTOU window between the comment and the checkout. zizmor flags `issue_comment` as a dangerous trigger and recommends that "a privileged user … add a label instead". `workflow_dispatch` and `repository_dispatch` always create runs, even from `GITHUB_TOKEN`, so the App needs no label or comment to chain runs.

## Current AFK loop (context)

- Trigger labels: `agent:implement` on `issues: labeled` ([afk-run.yml](../../.github/workflows/afk-run.yml)) and on `pull_request_target: labeled` ([afk-run-pr.yml](../../.github/workflows/afk-run-pr.yml)); `agent:update-branch` on `pull_request_target: labeled` ([afk-update-branch.yml](../../.github/workflows/afk-update-branch.yml)). Both PR workflows give one reason for `pull_request_target`: a `pull_request` run does not start on a conflicting PR.
- State labels: `agent:queued`, `agent:blocked`; [afk-promote-queued.yml](../../.github/workflows/afk-promote-queued.yml) swaps `agent:queued` for `agent:implement` with the App's token.
- A workflow-level concurrency group `afk-run` with `queue: max`. Events for other labels get a group keyed on `run_id`, so that they do not queue behind an AFK run.
- `claude-code-action` runs with the App's read token and `allowed_bots: ${{ vars.AFK_APP_SLUG }}`, so that App-started label events pass the action's bot check.
- [claude.yml](../../.github/workflows/claude.yml) already uses `issue_comment` with an owner-login check and a `zizmor: ignore[dangerous-triggers]` comment.

## 1. How first-party agents are triggered and report state

### GitHub Copilot cloud agent (formerly "coding agent")

- **Triggers.** The maintainer assigns an issue to Copilot from the issue sidebar, the issues list or Projects ([use-cloud-agent-on-github.md L130–175](https://github.com/github/docs/blob/8e7396e5e2e02bac9caba10c8d944f938bcd9b52/content/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-on-github.md#L130-L175)). The REST and GraphQL APIs can do the same: `replaceActorsForAssignable` or `addAssigneesToAssignable` with the `copilot-swe-agent` bot and an optional `agentAssignment` input ([use-cloud-agent-via-the-api.md L97–242](https://github.com/github/docs/blob/607e60c495abe7a16ffda9a1aff86675f7893b0f/content/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-via-the-api.md#L97-L242)). An `@copilot` mention in a comment on any PR also starts a session, including "@copilot resolve the merge conflicts on this PR" (same file, [L204–243](https://github.com/github/docs/blob/8e7396e5e2e02bac9caba10c8d944f938bcd9b52/content/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-on-github.md#L204-L243)).
- **After assignment, issue comments are ignored.** The agent receives the issue and its comments once and "won't react to" later issue comments. Further instructions go on the PR (L168).
- **Who may trigger.** "Copilot only responds to comments from people who have write access to the repository" ([reusable](https://github.com/github/docs/blob/a31ee09ca842e9177e5be8b053dee2f4e8b29f8f/data/reusables/copilot/cloud-agent/write-access-required.md)). "Comments from users without write access are never presented to the agent" ([Risks and mitigations](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)).
- **State reporting.** An eyes reaction on the triggering comment, a "Copilot has started work" timeline event, a draft PR linked from the issue timeline, session logs, and a review request at the end (use-cloud-agent-on-github.md L130–135, L225–231). Copilot does not report state through labels.
- **Actions on its PRs.** "By default, GitHub Actions workflows will not run automatically when Copilot pushes changes to a pull request"; a writer clicks **Approve and run workflows**. A repository admin can turn this off, with the warning that unreviewed code could "gain write access to your repository or access your GitHub Actions secrets" ([reusable](https://github.com/github/docs/blob/a31ee09ca842e9177e5be8b053dee2f4e8b29f8f/data/reusables/copilot/cloud-agent-workflow-run-approval-default.md); [configuring-agent-settings.md](https://github.com/github/docs/blob/8e7396e5e2e02bac9caba10c8d944f938bcd9b52/content/copilot/how-tos/use-copilot-agents/cloud-agent/configuring-agent-settings.md)).
- **Push limits.** Copilot pushes to one branch (`copilot/…` when it creates one), cannot run `git push` itself, cannot approve or merge, and the user who requested the PR cannot approve it ([Risks and mitigations](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)).
- **Copilot automations** (event- or schedule-driven runs). Triggers: schedule, issue created, PR opened, PR synchronised, API. By default automations "ignore events triggered by users who don't have write access", and they can be set to ignore events caused by Copilot itself ([about-automations](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/about-automations); [create-automations.md L72–78](https://github.com/github/docs/blob/d94121d98232ec1f7be524bc5ab42002d44603c5/content/copilot/how-tos/use-copilot-agents/cloud-agent/create-automations.md#L72-L78)). The documented triggers include no label trigger.

### anthropics/claude-code-action (source at [`9fa6885`](https://github.com/anthropics/claude-code-action/tree/9fa68854da5fadef4ed3dce240325a0dfe251880), 2026-11-13)

- **Triggers.** `trigger_phrase` (default `@claude`), `assignee_trigger` and `label_trigger` (default `claude`) ([action.yml L8–18](https://github.com/anthropics/claude-code-action/blob/9fa68854da5fadef4ed3dce240325a0dfe251880/action.yml#L8-L18)). The phrase must stand as a whole word in a comment, review, or issue/PR body or title. `label_trigger` matches only `issues` events with action `labeled`, so a PR label does not trigger the action ([trigger.ts L64–78, L175–183](https://github.com/anthropics/claude-code-action/blob/9fa68854da5fadef4ed3dce240325a0dfe251880/src/github/validation/trigger.ts#L64-L183)).
- **Author check.** On comment and review events, the action ignores deleted comments and comments that the actor did not write, so a moderator's edit cannot start a run ([trigger.ts L20–37](https://github.com/anthropics/claude-code-action/blob/9fa68854da5fadef4ed3dce240325a0dfe251880/src/github/validation/trigger.ts#L20-L37)).
- **Permission check.** The action calls `repos.getCollaboratorPermissionLevel` for `GITHUB_ACTOR` and accepts only `admin` or `write`. A login ending in `[bot]` passes the check and is handled by the separate human-actor check ([permissions.ts L145–208](https://github.com/anthropics/claude-code-action/blob/9fa68854da5fadef4ed3dce240325a0dfe251880/src/github/validation/permissions.ts#L145-L208)). For `workflow_run`, the action also checks the upstream run's actor and the fork owner (L31–72). `checkHumanActor` rejects non-`User` accounts unless they are listed in `allowed_bots` ([actor.ts L38–80](https://github.com/anthropics/claude-code-action/blob/9fa68854da5fadef4ed3dce240325a0dfe251880/src/github/validation/actor.ts#L38-L80)), and agent mode also runs it ([modes/agent/index.ts L54](https://github.com/anthropics/claude-code-action/blob/9fa68854da5fadef4ed3dce240325a0dfe251880/src/modes/agent/index.ts#L54)). The docs warn that "Allowed bots are not checked for repository permissions". `workflow_dispatch`, `repository_dispatch` and `schedule` are not checked separately, because "GitHub itself requires write access to dispatch a workflow" ([docs/security.md L5–8](https://github.com/anthropics/claude-code-action/blob/9fa68854da5fadef4ed3dce240325a0dfe251880/docs/security.md#L5-L8)).
- **TOCTOU pinning.** For an open PR, the action checks out `headRefOid` and fails in two cases ([branch.ts L208–235, L389–410](https://github.com/anthropics/claude-code-action/blob/9fa68854da5fadef4ed3dce240325a0dfe251880/src/github/operations/branch.ts#L208-L235)):
  - On `pull_request*` events, when the event's `head.sha` differs from `headRefOid`.
  - On comment events, when the repository Activity API shows that the head was pushed at or after the trigger time. The trigger time is the comment's `created_at`, or the label or assignment event time ([fetcher.ts L44–100](https://github.com/anthropics/claude-code-action/blob/9fa68854da5fadef4ed3dce240325a0dfe251880/src/github/data/fetcher.ts#L44-L100)).
- **State.** In tag mode, the action posts a "Claude Code is working…" tracking comment with a link to the run and updates it at the end ([create-initial.ts](https://github.com/anthropics/claude-code-action/blob/9fa68854da5fadef4ed3dce240325a0dfe251880/src/github/operations/comments/create-initial.ts); [common.ts L33](https://github.com/anthropics/claude-code-action/blob/9fa68854da5fadef4ed3dce240325a0dfe251880/src/github/operations/comments/common.ts#L33)). `use_sticky_comment` and `track_progress` select a single comment and a tracking comment on label events ([action.yml L116–143](https://github.com/anthropics/claude-code-action/blob/9fa68854da5fadef4ed3dce240325a0dfe251880/action.yml#L116-L143)). The action uses no labels for state.
- **Example workflow.** `issue_comment`, `pull_request_review_comment`, `issues: [opened, assigned]` and `pull_request_review` ([examples/claude.yml](https://github.com/anthropics/claude-code-action/blob/9fa68854da5fadef4ed3dce240325a0dfe251880/examples/claude.yml)). The repository's own `agent-approval-check` example combines `pull_request_target` with `issue_comment` ([examples/agent-approval-check.yml](https://github.com/anthropics/claude-code-action/blob/9fa68854da5fadef4ed3dce240325a0dfe251880/examples/agent-approval-check.yml)).

### GitHub Agentic Workflows (gh-aw), a first-party compiler from Markdown to Actions workflows

- **Triggers.** `slash_command` responds to `/name` as the first word of an issue, PR or comment body. Command workflows default to `reaction: eyes` and `status-comment: true`, which posts started and completed updates with a link to the run ([Command triggers](https://github.github.com/gh-aw/reference/command-triggers/)). `label_command` fires when a label is added to an issue, PR or discussion. It "automatically removes that label so it can be re-applied to re-trigger" and covers PRs through `pull_request: labeled`, not `pull_request_target` ([Triggers](https://github.github.com/gh-aw/reference/triggers/)).
- **Authorisation.** `on.roles` is an exact-match allowlist of roles that defaults to `[admin, maintainer, write]`, checked through `getCollaboratorPermissionLevel` ([check_permissions_utils.cjs L253–260](https://github.com/github/gh-aw/blob/5079ed9f2f43827723f7f35cae19bdecff06165b/actions/setup/js/check_permissions_utils.cjs#L253-L260)). The same file rejects confused-deputy cases where a bot actor differs from the PR, review or comment author (L107–145). Bots in `on.bots` must be installed on the repository.
- **Noise.** Command triggers listen to "all comment-related events, which can create skipped runs"; `events:` narrows them. A bot allowed to post commands can end up "occupying the concurrency slot", and "cancel-in-progress is disabled for command-trigger workflows" ([Command triggers](https://github.github.com/gh-aw/reference/command-triggers/)).
- **TOCTOU.** The gh-aw source states that review events bind to the reviewed commit, while "issue comments select the current head, not a historically approved revision" ([checkout_pr_branch.cjs L17–20](https://github.com/github/gh-aw/blob/5079ed9f2f43827723f7f35cae19bdecff06165b/actions/setup/js/checkout_pr_branch.cjs#L17-L20)).

## 2. GitHub security guidance per trigger

### `pull_request_target`

- **The 2026-12-02 block.** Enforcement covers public repositories "without an applicable Actions event policy". It excludes private and internal repositories and does not replace an existing event policy. The docs name no exception for same-repository branches, collaborators or bots. To keep the trigger, a policy that explicitly allows `pull_request_target` is required, optionally scoped to specific workflow files ([Securely using pull_request_target](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target); [changelog 2026-11-02](https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2); [changelog 2026-09-17](https://github.blog/changelog/2026-09-17-workflow-execution-protections-in-github-actions-generally-available/)). Brownouts ran on 2026-11-09 and 2026-11-16, 16:00–18:00 UTC; blocked runs "will create failed runs with an error annotation".
- **Event policies for this repository.** Policies live under Settings → Actions → Policies at repository level, with event rules (`restrict_action_events`), actor rules and a `workflow_path` condition ([Control workflow execution](https://docs.github.com/en/actions/how-tos/administer/control-workflow-execution); [REST: Actions policies](https://docs.github.com/en/rest/actions/policies)). A read-only `gh api repos/ltowarek/dust-mite/actions/policies` returned one repository-level policy ("Require lockfile", active), so repository-level policies work on this personal-account repository. Unverified: whether an event rule scoped by `workflow_path` lifts the default block for only those files.
- **Conflicts.** `pull_request` workflows do not run on a PR with a merge conflict, but "workflows with the `pull_request_target` event will run even if the pull request has a merge conflict" ([events-that-trigger-workflows.md L466](https://github.com/github/docs/blob/63859c481b2195607ff94c4dda765fb131a34759/content/actions/reference/workflows-and-actions/events-that-trigger-workflows.md#L466)).
- **Labels as a gate.** Security Lab Part 1 calls a "safe to test" label a stopgap that "is still prone to a race condition" ([Part 1](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/)). Part 4 recommends label gates over `issue_comment` and checking out `head.sha` ("a reliable and immutable pointer") rather than the head ref ([Part 4](https://securitylab.github.com/resources/github-actions-new-patterns-and-mitigations/)).

### `issue_comment`

- Runs with `GITHUB_REF` set to the default branch and `GITHUB_SHA` set to its last commit, for comments on issues and PRs. `github.event.issue.pull_request` tells the two apart ([events-that-trigger-workflows.md L267–300](https://github.com/github/docs/blob/63859c481b2195607ff94c4dda765fb131a34759/content/actions/reference/workflows-and-actions/events-that-trigger-workflows.md#L267-L300)).
- **Conflicting PRs.** The merge-conflict exclusion is documented only for `pull_request`, and `issue_comment` does not use the merge ref, so `issue_comment` runs on conflicting PRs. This is inferred; the docs do not state it explicitly. The Copilot docs accept "@copilot resolve the merge conflicts" on a PR, but Copilot is not an Actions trigger.
- **Not affected by the block.** None of the block sources lists `issue_comment`.
- **Security Lab Part 4 ("IssueOops")** ([Part 4](https://securitylab.github.com/resources/github-actions-new-patterns-and-mitigations/)):
  - Workflows "can be vulnerable to TOCTOU attacks": a writer approves a harmless PR by comment, then its author pushes malicious code.
  - The trigger "is not subject to the pull request approval mechanisms".
  - Checking only the commenter "is ineffective", because the commenter may not be the person who controls the code.
  - Comparing the comment time with the commit time "is also unreliable", because commit dates are author-controlled. `claude-code-action` instead compares against the push time from the Activity API (see section 1).
  - Part 4 recommends label gates and the commit SHA.
- **zizmor `dangerous-triggers`** flags `issue_comment` "as of v1.31.0", alongside `pull_request_target` and `workflow_run`. It advises: "Consider replacing `issue_comment` based developer workflows with workflows that require a privileged user to add a label" ([audits.md L466–540](https://github.com/zizmorcore/zizmor/blob/cf6865501ab4d220f2b5c72d9e8972d17bcea3d4/docs/audits.md#L466-L540)). The repository's pinned zizmor, 1.32.0 per commit `5e604f7`, therefore needs an ignore comment, as [claude.yml](../../.github/workflows/claude.yml) already has.
- **Untrusted input.** `github.event.comment.body` is untrusted input and goes through an intermediate environment variable, never inline `${{ }}` in `run:` ([Security Lab Part 2](https://securitylab.github.com/resources/github-actions-untrusted-input/); [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use#good-practices-for-mitigating-script-injection-attacks)).

### Authorising a commenter

- **`author_association` is not a permission level.** The schema defines `COLLABORATOR` as "Author has been invited to collaborate on the repository" and `MEMBER` as membership of the owning organisation; neither implies write access ([GraphQL schema, `CommentAuthorAssociation`](https://docs.github.com/public/fpt/schema.docs.graphql)). A read-only collaborator therefore passes an `author_association`-based check such as the Gemini example's.
- **Collaborator-permission API.** `GET /repos/{owner}/{repo}/collaborators/{username}/permission` returns `permission` (`admin`, `write`, `read`, `none`, where "maintain … is mapped to write and the triage role … to read") and `role_name` ([REST docs](https://docs.github.com/en/rest/collaborators/collaborators#get-repository-permissions-for-a-user)). `claude-code-action`, `codex-action`, gh-aw and `github/command` all use this check.
- **`actor` vs `triggering_actor`.** `github.actor` is the user that triggered the initial run. A re-run keeps that user's privileges even when `github.triggering_actor` differs ([contexts.md L181, L214](https://github.com/github/docs/blob/03d2e24b34bd88c361f1185f0aae1c46062c6510/content/actions/reference/workflows-and-actions/contexts.md#L181)). zizmor `bot-conditions` calls `github.actor == '…[bot]'` "spoofable" and recommends an identity bound to the payload object, for example `github.event.pull_request.user.login` ([audits.md L255–300](https://github.com/zizmorcore/zizmor/blob/cf6865501ab4d220f2b5c72d9e8972d17bcea3d4/docs/audits.md#L255-L300)). For comments, the equivalent is `github.event.comment.user`, checked against the actor as `claude-code-action` and gh-aw do.
- **IDs vs logins.** `github.actor_id` and `comment.user.id` are account IDs, "different from the actor username" ([reusable](https://github.com/github/docs/blob/24a7a1dca982b66ffe56e2c51faad1f83a12b3bf/data/reusables/actions/actor_id-description.md)). After a username change, the old login becomes available to other accounts ([Changing your username](https://docs.github.com/articles/changing-your-github-username)), so a login allowlist can match a different account. Comparing against a stored ID, such as `vars.AFK_APP_BOT_ID`, avoids this. This is inferred; no GitHub page states it as guidance.
- **Edited and deleted comments.** `issue_comment` also fires on `edited` and `deleted`. `claude-code-action` and `slash-command-dispatch` (`allow-edits: false`) ignore edits by default ([slash-command-dispatch README L80](https://github.com/peter-evans/slash-command-dispatch/blob/6575f453ef9056d9c8385a41b9db7dd6092fe007/README.md#L80)).

### Other triggers

- **`workflow_dispatch`.**
  - The run uses the workflow file of the dispatched ref, and "Once a workflow has run at least once, you can dispatch it against any branch or tag" ([events L1070–1079](https://github.com/github/docs/blob/63859c481b2195607ff94c4dda765fb131a34759/content/actions/reference/workflows-and-actions/events-that-trigger-workflows.md#L1070-L1079)). A writer can therefore run a modified workflow from a branch; in this repository the App has no Workflows permission.
  - Dispatching requires the fine-grained **Actions: write** permission (GitHub docs data [`fine-grained-pat-permissions.json`](https://github.com/github/docs/tree/main/src/github-apps/data/fpt-2026-03-10)), and the response includes `workflow_run_id` ([REST](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event)).
  - The Actions policies docs recommend restricting `workflow_dispatch` "so untrusted identities can't start workflows" ([About Actions policies](https://docs.github.com/en/actions/concepts/about-actions-policies)).
- **`repository_dispatch`.** Uses the default branch's workflow file and requires **Contents: write**. The payload allows at most 10 top-level properties and less than 64 KB ([REST](https://docs.github.com/en/rest/repos/repos#create-a-repository-dispatch-event); [events L902–918](https://github.com/github/docs/blob/63859c481b2195607ff94c4dda765fb131a34759/content/actions/reference/workflows-and-actions/events-that-trigger-workflows.md#L902-L918)).
- **`workflow_run`.** Privileged, and "can often be initiated by an attacker". Artifacts are untrusted, and owner checks are "not effective" ([Part 4](https://securitylab.github.com/resources/github-actions-new-patterns-and-mitigations/)). Chains stop after three levels ([events L1150](https://github.com/github/docs/blob/63859c481b2195607ff94c4dda765fb131a34759/content/actions/reference/workflows-and-actions/events-that-trigger-workflows.md#L1150)). zizmor flags it.
- **`issues: labeled`.** Default-branch context. Neither zizmor nor the block names it. Who may label is enforced by GitHub's permission model; that triage is the minimum role is unverified here. Its main residual risk is untrusted issue text reaching the agent.
- **`schedule`.** Default branch only. The `actor` can change, for example to whoever changed the default branch ([events L957–988](https://github.com/github/docs/blob/63859c481b2195607ff94c4dda765fb131a34759/content/actions/reference/workflows-and-actions/events-that-trigger-workflows.md#L957-L988)).

## 3. Which tokens start new runs, and how to chain

- Events caused by `GITHUB_TOKEN` "will not create a new workflow run", with two exceptions ([reusable](https://github.com/github/docs/blob/24a7a1dca982b66ffe56e2c51faad1f83a12b3bf/data/reusables/actions/actions-do-not-trigger-workflows.md)):
  - "`workflow_dispatch` and `repository_dispatch` events always create workflow runs".
  - `pull_request` `opened`, `synchronize` and `reopened` create runs in an approval-required state.
- A GitHub App installation token or PAT does start runs ([trigger-a-workflow.md L24–32](https://github.com/github/docs/blob/1484a08c7c5658e8f2c336d7422eba111f48f564/content/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow.md#L24-L32)). An App-added label or App-posted comment therefore starts `issues`, `pull_request_target` or `issue_comment` workflows.

| Chaining method | Token needed | Trade-offs |
|---|---|---|
| App re-adds a label (current) | App, Issues or PR write | State and trigger in one place; visible in the timeline. Each label change starts runs for every `labeled` workflow. |
| App posts a command comment | App, Issues write | Visible audit trail. The authorisation check must allow the App bot by ID, and `claude-code-action` needs `allowed_bots`. Every App comment also starts a run (noise). |
| `workflow_dispatch` | Actions: write (`GITHUB_TOKEN` suffices; the App has Actions read only) | No timeline noise, typed `inputs`, returns a run ID. No visible event on the ticket unless the workflow comments. |
| `repository_dispatch` | Contents: write (`GITHUB_TOKEN` or App) | Arbitrary `client_payload`; default-branch workflow only. The ChatOps pattern used by `slash-command-dispatch`. |
| `workflow_run` | none | Privileged, three-level limit, artifact-poisoning risk; flagged by zizmor. |

`peter-evans/slash-command-dispatch` parses commands in an `issue_comment` workflow and re-emits them as `repository_dispatch` or `workflow_dispatch`, so that comment parsing does not back up the workflow queue ([README L9–20](https://github.com/peter-evans/slash-command-dispatch/blob/6575f453ef9056d9c8385a41b9db7dd6092fe007/README.md#L9-L20)). gh-aw likewise relays slash commands from a side repository through `workflow_dispatch` ([Command triggers](https://github.github.com/gh-aw/reference/command-triggers/)).

## 5. Queueing and concurrency

- `queue` exists and accepts `single` (the default, at most one pending run) or `max` ("Up to 100 jobs or workflow runs can be `pending`"; when the queue is full, further runs are cancelled). `queue: max` together with `cancel-in-progress: true` is a validation error. Order is FIFO by the time each run "started waiting on the concurrency group", so ordering "is not guaranteed" ([actions-group-concurrency.md L15–26](https://github.com/github/docs/blob/336b7f546d9443dab4e1fa4f0f470e45448c7abc/data/reusables/actions/actions-group-concurrency.md#L15-L26); [limits.md L38](https://github.com/github/docs/blob/6946b3e28545f43dcd54d528966bcea34b17da63/content/actions/reference/limits.md#L38)). Group names are case-insensitive.
- Workflow-level `concurrency` may use only the `github`, `inputs` and `vars` contexts. Job-level concurrency may also use `needs`, `strategy` and `matrix` ([contexts.md L88–90](https://github.com/github/docs/blob/03d2e24b34bd88c361f1185f0aae1c46062c6510/content/actions/reference/workflows-and-actions/contexts.md#L88-L90)).
- **Skipped runs in the group.** No GitHub page states whether a run whose jobs all have a false `if:` still waits in a workflow-level group (unverified). Workflow-level concurrency is resolved before any job's `if:`, so such a run is expected to queue behind the active run. The current `run_id` fallback group exists to avoid this. Job-level `concurrency` on the guarded job avoids the question, because a skipped job never enters the group (inferred). gh-aw's note that a bot command can end up "occupying the concurrency slot" points the same way.
- **Noise from `issue_comment`.** Every comment on every issue and PR starts a run. With AFK, this includes the App's refusal, error, follow-up and covered-follow-up comments. Mitigations:
  - Narrow `types: [created]`.
  - Guard with a cheap job-level `if:` (`startsWith(github.event.comment.body, '/…')` and an `issue.pull_request` check).
  - Key a workflow-level group on the parsed command, as the current label workflows do.
  - Or move the guarded work to a job-level group.
  - Or dispatch from a thin parser workflow, as slash-command-dispatch does.
  - GitHub marks a workflow run whose jobs were all skipped as "skipped" rather than failed (secondary: [community discussion 8336](https://github.com/orgs/community/discussions/8336)).

## 6. GitHub guidance specific to AI agents in Actions

- **Copilot cloud agent** ([Risks and mitigations](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)):
  - Accepts triggers and comments only from users with write access.
  - "Filters hidden characters" and drops HTML comments before input reaches the agent.
  - Restricts the agent's internet access through a firewall.
  - Pushes to a single branch, with no `git push` of its own.
  - Starts no Actions run on its PRs until a human approves.
  - Signs its commits and links session logs.
  - Automations default to ignoring events from non-writers, and "Only this issue" limits write scope to the triggering item.
- **gh-aw security architecture** ([Architecture](https://github.github.com/gh-aw/introduction/architecture/)):
  - A read-only agent job, with writes deferred to separate safe-output jobs with narrow permissions. The AFK loop already follows this split: a read token for the agent and a write token minted afterwards.
  - A threat-detection job.
  - An egress firewall with a domain allowlist.
  - Input sanitisation that neutralises @mentions and bot triggers.
  - Role checks before activation.
  - `min-integrity: approved` applied automatically for public repositories.
- **`claude-code-action`** ([docs/security.md](https://github.com/anthropics/claude-code-action/blob/9fa68854da5fadef4ed3dce240325a0dfe251880/docs/security.md)):
  - Strips HTML comments, invisible characters and hidden attributes from input.
  - `include_comments_by_actor` allowlists whose comments reach the model.
  - On PRs from non-writers, it denies tools that run code.
  - "Auto mode is a review, not a boundary".
  - Recommends against checking out an untrusted ref into the workspace root under `pull_request_target`.
- **`codex-action`** lists PR bodies (hidden HTML comments), repository instruction files from PR content, and screenshots as prompt-injection vectors ([docs/security.md L11–18](https://github.com/openai/codex-action/blob/13e9c17417b29e9a276f73ec6ed7fb574137d3c3/docs/security.md#L11-L18)).
- **Security Lab Part 3.** Keep `GITHUB_TOKEN` least-privilege. The token is "quite permissive" on comment-triggered workflows and is available to every referenced action ([Part 3](https://securitylab.github.com/resources/github-actions-building-blocks/)).
- **Reported attacks (secondary sources).**
  - "Comment and Control" (2026-04) reported hijacking `claude-code-action`, the Gemini CLI action and the Copilot agent through PR titles, issue bodies and comments ([SecurityWeek](https://www.securityweek.com/claude-code-gemini-cli-github-copilot-agents-vulnerable-to-prompt-injection-via-comments/)).
  - "GitLost" (2026-07) reported data leaking from gh-aw through a public issue ([The Next Web](https://thenextweb.com/news/gitlost-github-ai-agent-leaks-private-repos?type=Security)).
  - Neither report was verified against the original disclosures.

Notes for the decision:

- **Keeping labels as triggers.** The smallest change that survives 2026-12-02 is a repository Actions event policy that allows `pull_request_target`, scoped to the two PR workflows. zizmor and Security Lab Part 4 favour label gates over comment commands. The open question is whether path-scoped policies behave as described (unverified).
- **Moving to `issue_comment`.** The move matches the first-party agents' user experience. It brings in four things labels do not need: a permission check, an author-equals-actor check, head-SHA plus push-time TOCTOU pinning (`claude-code-action` implements all three), and noise control for the App's own comments.
- **Chaining.** `workflow_dispatch` or `repository_dispatch` is the idiomatic chaining channel, needs no App-authored trigger text, and works with `GITHUB_TOKEN`. A label or comment would then be needed only where a human acts.
